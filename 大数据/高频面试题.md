### 1.2.2 HDFS读流程和写流程

🔥 **写流程**：
1. 客户端向 NameNode 请求上传文件
2. NameNode 检查权限和目录结构，响应可以上传
3. 客户端请求上传第一个 Block，NameNode 返回 DataNode 列表（如 dn1、dn2、dn3）
4. 客户端与 dn1 建立传输通道，dn1→dn2→dn3 形成 **Pipeline**
5. 数据以 **Packet（64KB）** 为单位传输，每个 Packet 由多个 **Chunk（512B+4B校验）** 组成
6. 传输完一个 Block 后，继续请求下一个 Block 的 DataNode 列表

🔥 **读流程**：
1. 客户端向 NameNode 请求下载文件
2. NameNode 返回文件的 Block 列表及所在 DataNode（按距离排序）
3. 客户端选择最近的 DataNode 读取 Block
4. 串行读取所有 Block，合并成完整文件

### 1.2.3 HDFS小文件处理

🔥 **危害**：每个文件/目录/Block 在 NameNode 占约 **150B** 内存。1亿小文件 ≈ 15GB NameNode 内存。

**解决方案**：
1. **HAR 归档**：将小文件合并成一个 HAR 文件，减少 NameNode 压力
2. **CombineTextInputFormat**：MR 输入时合并多个小文件为一个切片
3. **JVM 重用**：减少 JVM 启停开销（`mapreduce.job.jvm.numtasks=10`）
4. **Hive 合并**：`SET hive.merge.mapfiles=true;`（Map 输出合并小文件）
5. **源头控制**：采集时用 Flume 的 rollSize/rollInterval 控制文件大小

### 1.2.4 HDFS的NameNode内存

- **生产配置**：NameNode 堆内存通常设为 **总内存的1/4~1/2**，最大不超过 128GB
- **计算方式**：文件数 × 150B × 3（副本元数据开销因子）
- **配置参数**：`hadoop-env.sh` 中 `HADOOP_NAMENODE_OPTS=-Xmx100g`
- 1亿文件约需 **60GB** 以上 NameNode 内存

### 1.2.5 Shuffle及优化

🔥 **Shuffle 流程**：

**Map 端**：Map 输出 → 环形缓冲区（100MB，80%溢写阈值）→ 分区 + 排序 → 溢写到磁盘 → 多个溢写文件 Merge 合并

**Reduce 端**：Copy 拉取数据 → 内存/磁盘缓冲 → 归并排序 → 交给 Reducer 处理

**优化**：
- 增大环形缓冲区：`mapreduce.task.io.sort.mb=512`
- 提高溢写阈值：`mapreduce.map.sort.spill.percent=0.9`
- 增加 Merge 合并次数：`mapreduce.task.io.sort.factor=20`
- **Combiner 预聚合**：减少 Shuffle 数据量（不影响最终结果的前提下）
- **压缩**：`mapreduce.map.output.compress=true`（Snappy/LZO）
- 调整 Reduce 拉取并行度：`mapreduce.reduce.shuffle.parallelcopies=10`

### 1.2.6 Yarn工作机制

🔥 **核心流程**（7步）：
1. Client 提交 Job 到 ResourceManager
2. RM 分配 Container，启动 **ApplicationMaster**
3. AM 向 RM 注册并申请资源
4. RM 将资源分配信息返回给 AM
5. AM 通知对应 NodeManager 启动 Container 运行 Task
6. 各 Task 向 AM 汇报进度和状态
7. 应用完成后，AM 向 RM 注销并释放资源

### 1.2.7 Yarn调度器

| 调度器 | 特点 | 适用场景 |
|--------|------|----------|
| **FIFO** | 先进先出，单队列 | 测试环境 |
| **Capacity Scheduler** | 多队列，每个队列有最低资源保证，队列内 FIFO | **Apache 默认**，大公司多部门 |
| **Fair Scheduler** | 多队列，队列内按权重公平分配 | **CDH 默认**，资源利用率高 |

🔥 **生产选择**：大部分公司使用 **Capacity Scheduler**，按业务线划分队列（如 default、hive、spark），配置 `yarn.scheduler.capacity.root.queues`。

### 1.2.8 HDFS块大小

- **默认块大小**：Hadoop 2.x/3.x 均为 **128MB**
- **设计原则**：寻址时间约为传输时间的 1%（磁盘 IO 约 100MB/s → 128MB 块约 1s 传输，寻址约 10ms）
- **调整建议**：SSD/高速网络可设为 256MB/512MB；不宜过小（增加 NameNode 压力）也不宜过大（MapTask 处理过慢）

### 1.2.9 Hadoop脑裂原因及解决办法？

🔥 **脑裂**：两个 NameNode 同时认为自己是 Active，导致数据不一致。

**原因**：ZK 心跳超时（网络抖动、NN Full GC），ZK 误判 Active NN 已死，触发切换，但原 Active NN 仍存活。

**解决方案（Fencing 隔离机制）**：
1. **sshfence**：通过 SSH 登录旧 Active NN，kill 掉 NameNode 进程
2. **shell**：执行自定义脚本，如 `fuser -k` 杀死进程
3. **配置**：`hdfs-site.xml` 中 `dfs.ha.fencing.methods` 设置 sshfence + shell 兜底


### 1.3.2 选举机制

🔥 **选举触发条件**：集群初次启动 或 Leader 宕机

**选举规则（优先级从高到低）**：
1. **Epoch**（Leader 任期号）大的优先
2. **ZXID**（事务ID）大的优先（数据越新）
3. **SID**（服务器ID）大的优先

**过半机制**：超过半数节点同意即当选 Leader。所以 ZK 集群建议 **奇数台**（3台/5台），最多允许 `(N-1)/2` 台宕机。

### 1.3.3 Zookeeper符合CAP法则中哪两个？

🔥 **CP**（一致性 + 分区容错性）：
- **C（Consistency）**：ZK 保证顺序一致性，Leader 处理所有写请求，通过 ZAB 协议同步到 Follower
- **P（Partition Tolerance）**：过半存活即可工作
- **不完全满足 A（Availability）**：Leader 选举期间（约 30s~120s）集群不可用

### 1.3.4 Zookeeper脑裂

**原因**：网络分区导致集群分成两部分，各自选出 Leader。

**ZK 的解决**：**过半机制**天然防脑裂。假设 5 台机器分成 3+2 两个分区，只有 3 台的那边能选出 Leader（满足过半），2 台的那边选不出（不满足过半），自动降级为 Follower。

### 1.3.5 Zookeeper用来干嘛了

🔥 **大数据场景中的应用**：

| 组件 | ZK 的作用 |
|------|-----------|
| **Hadoop HA** | NameNode 主备选举、自动故障转移 |
| **HBase** | Master 选举、RegionServer 上下线监控、Meta 表寻址 |
| **Kafka** | Broker 注册、Controller 选举、Consumer Offset（旧版） |
| **Flink** | JobManager HA 模式下的 Leader 选举 |
| **DolphinScheduler** | Master/Worker 节点监控与容错 |
| **Hive** | Metastore HA 模式下的主备切换 |

## 1.4 Flume

### 1.4.1 Flume组成，Put事务，Take事务

**三大组件**：Source（采集数据）→ Channel（缓冲队列）→ Sink（输出数据）

🔥 **Put 事务**（Source → Channel）：
1. `doPut`：将数据写入 Channel 临时缓冲区
2. `doCommit`：检查 Channel 是否有空间，有则提交
3. `doRollback`：Channel 满了则回滚

🔥 **Take 事务**（Channel → Sink）：
1. `doTake`：从 Channel 取数据
2. `doCommit`：Sink 发送成功则提交，从 Channel 删除数据
3. `doRollback`：发送失败则回滚，数据退回 Channel

### 1.4.2 Flume拦截器

**作用**：在 Source 写入 Channel 之前对 Event 进行修改或过滤。

**常用拦截器**：
- **Timestamp Interceptor**：在 Header 中添加时间戳
- **Host Interceptor**：添加主机名/IP
- **Static Interceptor**：添加固定 KV 对
- **Regex Filtering**：正则过滤
- **自定义拦截器**：实现 `Interceptor` 接口（如 ETL 清洗、日志类型分流）

**生产用法**：日志采集中用自定义拦截器做 **ETL清洗**（过滤不完整日志）和 **日志类型分流**（按 Header 中的 topic 分发到不同 Kafka Topic）。

### 1.4.3 Flume Channel选择器

| 选择器 | 说明 |
|--------|------|
| **Replicating**（默认） | 将 Event 复制到所有 Channel |
| **Multiplexing** | 根据 Event Header 中的某个字段路由到不同 Channel |

**生产用法**：配合拦截器实现日志分流，如根据日志类型将用户行为日志和启动日志分别发送到不同 Kafka Topic。

### 1.4.4 Flume监控器

- **Ganglia 监控**：Flume 内置 Ganglia 上报，监控 Event 吞吐量等
- **自定义监控**：通过 JMX 获取 Flume 指标，接入 Prometheus + Grafana
- **关键指标**：EventPutSuccessCount、EventTakeSuccessCount、ChannelSize、ChannelFillPercentage

### 1.4.5 Flume采集数据会丢失吗?

🔥 **不会丢失**（使用 FileChannel 时）：
- Channel 有两种：**MemoryChannel**（速度快，宕机丢数据）和 **FileChannel**（基于 WAL 日志，宕机不丢数据）
- Flume 有完善的事务机制（Put + Take 事务），保证 Source→Channel→Sink 各环节数据安全
- **生产建议**：使用 **KafkaChannel**（直接对接 Kafka），兼具高吞吐和数据可靠性，还省掉了 Sink 组件

### 1.4.6 Flume如何提高吞吐量

1. **增加 Agent 数量**：多个 Agent 并行采集
2. **增大 Channel 容量**：`capacity` 和 `transactionCapacity`
3. **增大 BatchSize**：`batchSize=1000`（一次批量写入更多 Event）
4. **使用 KafkaChannel**：省去 Sink，直接对接 Kafka，减少中间环节
5. **增大 JVM 内存**：Flume 启动参数 `-Xmx2g`
6. **文件 Sink 增大 rollSize**：如 `rollSize=134217728`（128MB）

## 1.5 Kafka

### 1.5.1 Kafka架构

🔥 **核心组件**：
- **Producer**：消息生产者
- **Consumer / Consumer Group**：消息消费者/消费者组
- **Broker**：Kafka 服务节点
- **Topic**：消息主题（逻辑分类）
- **Partition**：分区（物理分片，保证分区内有序）
- **Replica**：副本（Leader 负责读写，Follower 同步备份）
- **Zookeeper**：管理 Broker 注册、Controller 选举（Kafka 3.x 开始可用 KRaft 替代）

### 1.5.2 Kafka生产端分区分配策略

🔥 **发送消息时分区策略**：
1. **指定 Partition**：直接发往指定分区
2. **指定 Key**：对 Key 取 hash，再对分区数取模
3. **都不指定**：使用 **Sticky Partition**（粘性分区，Kafka 2.4+），一个 Batch 写满后随机切换分区（比之前的 Round-Robin 性能更好）

### 1.5.3 Kafka丢不丢数据

🔥 **三个环节分析**：

**Producer 端**：
- `acks=0`：不等确认，可能丢 ❌
- `acks=1`：Leader 确认，Leader 宕机可能丢 ⚠️
- `acks=-1(all)`：所有 ISR 副本确认，**不丢** ✅（配合 `min.insync.replicas≥2`）

**Broker 端**：
- 副本数 ≥ 2 + `min.insync.replicas≥2` → 不丢

**Consumer 端**：
- 手动提交 Offset（`enable.auto.commit=false`）→ 不丢（但可能重复消费）

### 1.5.4 Kafka的ISR副本同步队列

🔥 **ISR（In-Sync Replicas）**：与 Leader 保持同步的副本集合。

- Follower 如果超过 `replica.lag.time.max.ms`（默认 30s）未向 Leader 发送 Fetch 请求，会被踢出 ISR
- 被踢出的副本进入 **OSR**（Out-of-Sync Replicas）
- **AR = ISR + OSR**
- Leader 选举只从 ISR 中选取

### 1.5.5 Kafka数据重复

🔥 **原因**：Producer 发送消息后收到超时重试，但实际 Broker 已经写入成功 → 重复。

**解决方案**：
1. **幂等性**（Exactly-Once 语义单分区）：`enable.idempotence=true`，利用 PID + SequenceNumber 去重
2. **事务**（跨分区 Exactly-Once）：`transactional.id`，支持原子性写入多个分区
3. **Consumer 端去重**：利用唯一 ID + Redis/HBase 做业务幂等

### 1.5.6 Kafka如何保证数据有序or怎么解决乱序

🔥 **分区内有序**：单分区内消息按 Offset 严格有序。

**跨分区无法保证全局有序**。

**解决方案**：
1. **单分区**：所有消息写入一个分区（牺牲并行度）
2. **按 Key 分区**：相同 Key 的消息进同一分区（如按订单ID）
3. **配合幂等性**：`enable.idempotence=true` + `max.in.flight.requests.per.connection≤5`（Kafka 1.x+ 幂等模式下最多5个未确认请求仍保序）

### 1.5.7 Kafka分区Leader选举规则

- Controller 监控到 Leader 所在 Broker 宕机
- 从该分区的 **ISR 列表**中按照 **AR 中的排列顺序**选择第一个存活的副本作为新 Leader
- 如果 ISR 为空且 `unclean.leader.election.enable=true`，则从 OSR 中选（可能丢数据）

### 1.5.8 Kafka中AR的顺序

**AR**（Assigned Replicas）：分区创建时分配的所有副本列表，顺序在分区创建时确定且不变。ISR 列表的顺序与 AR 保持一致。

### 1.5.9 Kafka日志保存时间

- 默认保存 **7天**（`log.retention.hours=168`）
- 生产环境通常设为 **3天**（节省磁盘空间）
- 也可按大小控制：`log.retention.bytes`（默认 -1，不限制）

### 1.5.10 Kafka过期数据清理

| 策略 | 说明 | 配置 |
|------|------|------|
| **delete**（默认） | 直接删除过期的 Segment 文件 | `log.cleanup.policy=delete` |
| **compact** | 按 Key 保留最新 value，删除旧版本 | `log.cleanup.policy=compact` |

### 1.5.11 Kafka为什么能高效读写数据

🔥 **四大核心**：
1. **顺序写磁盘**：Partition 日志追加写入，顺序IO 比随机IO 快 600倍
2. **零拷贝（Zero-Copy）**：`sendfile()` 系统调用，数据直接从 PageCache 到网卡，不经过用户态
3. **PageCache**：利用操作系统页缓存，将磁盘数据缓存在内存中
4. **分区分段**：Topic 分 Partition，Partition 分 Segment（`.log` + `.index` + `.timeindex`），稀疏索引定位快

### 1.5.12 自动创建主题

- `auto.create.topics.enable=true`（默认开启）：Producer 向不存在的 Topic 发消息时自动创建
- **生产建议**：设为 `false`，防止误操作创建垃圾 Topic

### 1.5.13 副本数设定

- 生产环境通常设为 **2~3 个副本**
- 副本数不能超过 Broker 数量
- 副本越多 → 可靠性越高，但磁盘和网络开销越大

### 1.5.14 Kakfa分区数

🔥 **分区数设定**：
- **经验值**：Topic 分区数 = **期望吞吐量 / 单分区吞吐量**
- 单分区吞吐约 10~20 MB/s（取决于硬件）
- **生产经验**：日志 Topic 通常 3~6 个分区，高吞吐 Topic 可设 10+ 个分区
- 分区数只能增加不能减少

### 1.5.15 Kafka增加分区

```bash
# 将 topic 分区数增加到 6
bin/kafka-topics.sh --alter --topic my_topic \
  --partitions 6 --bootstrap-server hadoop102:9092
```

⚠️ 增加分区后，按 Key 分区的数据分布会改变（hash 结果变了）。

### 1.5.16 Kafka中多少个Topic

根据业务线划分，生产环境通常 **几十到上百个** Topic。例如：
- 用户行为日志 Topic（如 `topic_log`）
- 业务数据 Topic（如 `topic_db`）
- 各业务线独立 Topic

### 1.5.17 Kafka消费者是拉取数据还是推送数据

🔥 **Pull（拉取）模式**。

**优点**：Consumer 根据自身处理能力控制消费速度，不会被 Broker 淹没。
**缺点**：没数据时空轮询浪费 CPU → 解决方案：`fetch.min.bytes` + `fetch.max.wait.ms` 长轮询。

### 1.5.18 Kafka消费端分区分配策略

🔥 **三种策略**：

| 策略 | 说明 |
|------|------|
| **Range**（默认） | 按 Topic 维度，分区序号范围分配（可能不均匀） |
| **RoundRobin** | 所有 Topic 的所有分区打散后轮询分配（更均匀） |
| **Sticky** | 尽量保持原有分配不变，Rebalance 时最小迁移 |
| **CooperativeSticky** | 协作式粘性（Kafka 2.4+），增量式 Rebalance，不停止所有消费 |

### 1.5.19 消费者再平衡的条件

**Rebalance 触发条件**：
1. Consumer Group 中成员数量变化（新加入或退出）
2. 订阅的 Topic 数量变化
3. 订阅的 Topic 分区数变化

**Rebalance 过程**：JoinGroup → SyncGroup → 分配方案下发

### 1.5.20 指定Offset消费

```java
// 从指定 offset 开始消费
consumer.assign(Arrays.asList(new TopicPartition("topic", 0)));
consumer.seek(new TopicPartition("topic", 0), 100L); // 从 offset=100 开始
```

也可通过 `auto.offset.reset` 配置首次消费位置：`earliest`（最早）/ `latest`（最新，默认）。

### 1.5.21 指定时间消费

```java
Map<TopicPartition, Long> timestampMap = new HashMap<>();
timestampMap.put(new TopicPartition("topic", 0), 1638288000000L);
// 根据时间戳获取对应的 offset
Map<TopicPartition, OffsetAndTimestamp> offsets = consumer.offsetsForTimes(timestampMap);
// 然后用 seek 定位到该 offset
```

### 1.5.22 Kafka监控

🔥 **常用监控工具**：
- **Kafka Eagle（EFAK）**：Web 界面，支持 Topic/Consumer 监控、SQL 查询
- **Kafka Manager（CMAK）**：Yahoo 开源，集群管理
- **Prometheus + Grafana**：通过 JMX Exporter 采集 Kafka 指标
- **Burrow**：LinkedIn 开源，专注 Consumer Lag 监控

**核心监控指标**：Consumer Lag（积压量）、Broker 磁盘使用率、网络 IO、ISR 变化。

### 1.5.23 Kafka数据积压

🔥 **原因**：Consumer 消费速度 < Producer 生产速度。

**解决方案**：
1. **增加分区数 + 增加 Consumer 实例**（Consumer 数 ≤ 分区数）
2. **提高 Consumer 吞吐量**：增大 `max.poll.records`，优化消费逻辑
3. **如果是下游问题**：优化下游处理（如批量写入数据库）
4. **紧急处理**：创建临时 Topic（更多分区），用中转 Consumer 快速搬运数据

### 1.5.24 如何提升吞吐量

**Producer 端**：
- `batch.size=32768`（32KB→增大）
- `linger.ms=5`（等待更多消息凑 Batch）
- `buffer.memory=67108864`（64MB 缓冲区）
- `compression.type=snappy`

**Broker 端**：
- 增加分区数
- 合理设置 `num.network.threads` 和 `num.io.threads`

**Consumer 端**：
- 增加 `fetch.min.bytes` 和 `max.poll.records`

### 1.5.25 Kafka中数据量计算

**计算公式**：日数据量 = 条数 × 每条大小

例如：每天 1亿条日志，每条 1KB → 日数据量约 **100GB**。
考虑 2 副本 → 磁盘日增 200GB，保存 3 天 → 需要 **600GB** 磁盘空间。

### 1.5.26 Kafka如何压测？

```bash
# Producer 压测
bin/kafka-producer-perf-test.sh --topic test \
  --num-records 1000000 --record-size 1024 \
  --throughput -1 --producer-props bootstrap.servers=hadoop102:9092

# Consumer 压测
bin/kafka-consumer-perf-test.sh --topic test \
  --messages 1000000 --broker-list hadoop102:9092
```

关注指标：吞吐量（MB/s）、平均延迟、P99 延迟。

### 1.5.27 磁盘选择

- **机械硬盘（HDD）** 即可，因为 Kafka 是顺序写磁盘，HDD 顺序 IO 性能与 SSD 差距不大
- SSD 不是必须，性价比不高
- 建议 JBOD（多盘独立挂载，非 RAID）

### 1.5.28 内存选择

- Kafka **不依赖 JVM 堆内存**，主要靠 OS 的 **PageCache**
- JVM 堆内存设 **6~10GB** 足够
- **服务器总内存**建议 64GB+，更多内存 → 更大 PageCache → 更高性能

### 1.5.29 CPU选择

- Kafka 对 CPU 要求不高，**num.io.threads**（默认8）和 **num.network.threads**（默认3）是主要消耗
- 建议 16~32 核 CPU

### 1.5.30 网络选择

- Kafka 是 **网络 IO 密集型**，网络带宽是常见瓶颈
- 建议 **万兆网卡**（10Gbps）
- 计算：峰值吞吐 × 副本数 ≤ 网络带宽的 70%

### 1.5.31 Kafka挂掉

**排查步骤**：
1. 查看 Kafka 日志：`server.log`、`controller.log`
2. 常见原因：磁盘满、OOM（内存不足）、ZK 连接超时、网络故障
3. **恢复**：清理磁盘/增加内存后重启，Kafka 会自动恢复副本同步

### 1.5.32 Kafka的机器数量

**公式**：Broker 数 = 峰值吞吐量 / 单台 Broker 吞吐能力

例如：峰值 200MB/s，单台压测 50MB/s → 至少 **4 台 Broker**。生产建议预留 30% 余量 → **5~6 台**。

### 1.5.33 服役新节点退役旧节点

1. 新节点安装配置 Kafka，修改 `broker.id`（唯一），启动
2. 创建 `reassignment.json`，指定要迁移的 Topic 和分区
3. 执行：`kafka-reassign-partitions.sh --execute`
4. 验证：`kafka-reassign-partitions.sh --verify`
5. 数据迁移完成后关闭旧节点

### 1.5.34 Kafka单条日志传输大小

- 默认 **1MB**（`message.max.bytes=1048576`）
- 如果日志超过 1MB，需同时调整：
  - Broker：`message.max.bytes`
  - Producer：`max.request.size`
  - Consumer：`fetch.max.bytes` 和 `max.partition.fetch.bytes`

### 1.5.35 Kafka参数优化

| 参数 | 建议值 | 说明 |
|------|--------|------|
| `num.partitions` | 3~6 | 默认分区数 |
| `log.retention.hours` | 72 | 日志保留3天 |
| `log.segment.bytes` | 1073741824 | Segment 大小 1GB |
| `num.replica.fetchers` | 3 | 副本拉取线程数 |
| `replica.lag.time.max.ms` | 30000 | ISR 超时时间 |

## 1.6 Hive

### 1.6.1 Hive的架构

🔥 **核心组件**：
- **CLI/Beeline**：客户端，提交 HQL
- **Driver**：编译器（Compiler）、优化器（Optimizer）、执行器（Executor）
- **Metastore**：元数据存储（通常用 MySQL），记录表结构、分区、存储位置
- **执行引擎**：MR / Tez / **Spark**（生产推荐 Spark on Hive）

**执行流程**：HQL → 解析器（AST）→ 编译器（QueryBlock）→ 优化器（逻辑优化）→ 执行器（物理执行计划/MR Job）

### 1.6.2 HQL转换为MR流程

1. **解析器（Parser）**：HQL → AST（抽象语法树）
2. **语义分析（Semantic Analyzer）**：AST → QueryBlock
3. **逻辑计划生成**：QueryBlock → OperatorTree（TableScan、Select、Filter、Join、GroupBy 等算子）
4. **逻辑优化**：谓词下推、列裁剪、Map Join 优化等
5. **物理计划生成**：OperatorTree → TaskTree（一个或多个 MR/Spark Job）
6. **物理优化**：MapJoin 转换等
7. **提交执行**：生成 MR Job 提交到 YARN

### 1.6.3 Hive和数据库比较

| 对比项 | Hive | 数据库（MySQL） |
|--------|------|-----------------|
| 数据规模 | PB 级 | GB~TB 级 |
| 延迟 | 高（分钟级） | 低（毫秒级） |
| 数据格式 | Schema On Read | Schema On Write |
| 事务 | 有限支持（ACID 表） | 完整 ACID |
| 索引 | 有限 | 丰富（B+Tree 等） |
| 更新/删除 | 不擅长 | 擅长 |
| 执行引擎 | MR/Tez/Spark | 自有引擎 |

### 1.6.4 内部表和外部表

🔥 **核心区别**：

| | 内部表（Managed） | 外部表（External） |
|--|------------------|-------------------|
| 创建 | `CREATE TABLE` | `CREATE EXTERNAL TABLE` |
| 删除表 | 删元数据 + 删数据 | 只删元数据，**数据保留** |
| 适用场景 | 中间临时表 | ODS 层原始数据（推荐） |

**生产建议**：ODS 层用**外部表**（防止误删数据），DWD/DWS/ADS 层可用内部表。

### 1.6.5 系统函数

**高频函数**：`date_format`、`date_add`、`date_sub`、`datediff`、`nvl`、`coalesce`、`if`、`case when`、`concat_ws`、`collect_set/list`、`get_json_object`、`explode`、`lateral view`、`split`、`substr`

### 1.6.6 自定义UDF、UDTF函数

🔥 **三种类型**：
- **UDF**：一进一出（如字符串处理）
- **UDAF**：多进一出（如自定义聚合）
- **UDTF**：一进多出（如 `explode`，一行变多行）

**开发步骤**：
1. 继承 `GenericUDF` 或 `GenericUDTF`
2. 实现 `initialize()`、`evaluate()` / `process()` 方法
3. 打 jar 包上传 HDFS
4. `CREATE FUNCTION my_func AS 'com.xxx.MyUDF' USING JAR 'hdfs://path/to/jar'`

### 1.6.7 窗口函数

🔥 **语法**：`函数 OVER (PARTITION BY 分区列 ORDER BY 排序列 ROWS BETWEEN ... AND ...)`

**常用窗口函数**：

| 函数 | 说明 |
|------|------|
| `ROW_NUMBER()` | 顺序排名，不重复（1,2,3,4） |
| `RANK()` | 跳跃排名（1,2,2,4） |
| `DENSE_RANK()` | 密集排名（1,2,2,3） |
| `LAG(col, n)` | 取前 n 行的值 |
| `LEAD(col, n)` | 取后 n 行的值 |
| `FIRST_VALUE()` | 窗口第一个值 |

| `SUM/COUNT/AVG OVER()` | 窗口聚合 |

### 1.6.8 Hive优化

#### 1.6.8.1 分组聚合

🔥 **开启 Map 端预聚合**（Combiner）：
```sql
SET hive.map.aggr=true;  -- 默认开启
SET hive.groupby.mapaggr.checkinterval=100000;  -- 预聚合检查行数
```

#### 1.6.8.2 Map Join

🔥 小表 JOIN 大表时，将小表加载到内存（Map 端完成 JOIN，无需 Reduce）：
```sql
SET hive.auto.convert.join=true;  -- 默认开启
SET hive.mapjoin.smalltable.filesize=25000000;  -- 小表阈值 25MB
```

#### 1.6.8.3 SMB Map Join

**Sort Merge Bucket Map Join**：两个大表都按 Join Key 分桶且桶数相同，一个桶对应一个桶做 Join。
```sql
SET hive.optimize.bucketmapjoin=true;
SET hive.optimize.bucketmapjoin.sortedmerge=true;
```

#### 1.6.8.4 Reduce并行度

```sql
-- 调整每个 Reduce 处理的数据量（默认 256MB）
SET hive.exec.reducers.bytes.per.reducer=256000000;
-- 设置最大 Reduce 数
SET hive.exec.reducers.max=1009;
```

#### 1.6.8.5 小文件合并

```sql
-- Map 输入合并小文件
SET hive.input.format=org.apache.hadoop.hive.ql.io.CombineHiveInputFormat;
-- Map 输出合并
SET hive.merge.mapfiles=true;
-- Reduce 输出合并
SET hive.merge.mapredfiles=true;
-- 合并后文件大小目标 256MB
SET hive.merge.size.per.task=256000000;
```

#### 1.6.8.6 谓词下推

🔥 将 WHERE 条件尽量下推到 Map 端，减少 Shuffle 数据量：
```sql
SET hive.optimize.ppd=true;  -- 默认开启
```

**注意**：外连接中 ON 和 WHERE 的区别——ON 的条件在 JOIN 前过滤，WHERE 在 JOIN 后过滤。

#### 1.6.8.7 并行执行

多个无依赖的 Stage 并行执行：
```sql
SET hive.exec.parallel=true;
SET hive.exec.parallel.thread.number=8;
```

#### 1.6.8.8 CBO优化

**Cost-Based Optimizer**：基于统计信息（表大小、行数、列基数等）选择最优执行计划：
```sql
SET hive.cbo.enable=true;  -- 默认开启
ANALYZE TABLE t COMPUTE STATISTICS;
ANALYZE TABLE t COMPUTE STATISTICS FOR COLUMNS;
```

#### 1.6.8.9 列式存储

🔥 **ORC**（推荐）或 Parquet 格式，按列存储，配合压缩（Snappy/ZLIB），大幅减少读取量和存储空间。

#### 1.6.8.10 压缩

| 阶段 | 推荐压缩 |
|------|----------|
| Map 输出 | Snappy（速度快） |
| 最终输出 | ZLIB/LZO（压缩率高） |

#### 1.6.8.11 分区和分桶

- **分区（Partition）**：按日期等字段分目录，查询时过滤无关分区
- **分桶（Bucket）**：按字段 hash 分文件，提升 JOIN 和采样效率

#### 1.6.8.12 更换引擎

将执行引擎从 MR 切换为 **Tez** 或 **Spark**，速度大幅提升：
```sql
SET hive.execution.engine=spark;
```

#### 1.6.8.13 几十张表join 如何优化

1. **按业务拆分**：避免一次 SQL 关联太多表，分步骤计算
2. **Map Join**：小表广播
3. **先过滤再 Join**：减少参与 Join 的数据量
4. **公共结果复用**：用临时表存储中间结果
5. **调整 Join 顺序**：小表在前，大表在后

### 1.6.9 Hive解决数据倾斜方法

🔥 **数据倾斜原因**：某个 Key 数据量远超其他 Key，导致个别 Reduce 处理数据量过大。

**解决方案**：
1. **分组聚合倾斜**：`SET hive.groupby.skewindata=true;`（两阶段聚合：第一阶段随机分区预聚合，第二阶段按 Key 聚合）
2. **Join 倾斜 - 大表 join 小表**：Map Join（小表广播）
3. **Join 倾斜 - 大表 join 大表**：
   - 过滤空 Key / 异常 Key
   - 对倾斜 Key 加随机前缀打散 + 另一侧扩容（两阶段 Join）
4. **Count Distinct 倾斜**：改为 `GROUP BY + COUNT`

### 1.6.10 Hive的数据中含有字段的分隔符怎么处理？

1. **使用不常见分隔符**：如 `\001`（Ctrl+A），Hive 默认分隔符
2. **数据预处理**：在 ETL 阶段替换掉数据中的分隔符
3. **使用 SerDe**：如 `OpenCSVSerde`、`RegexSerDe` 处理复杂格式
4. **使用 JSON/ORC/Parquet** 格式，不依赖文本分隔符

### 1.6.11 MySQL元数据备份

```bash
# 每天定时备份 Hive Metastore 的 MySQL 数据库
mysqldump -uroot -p metastore > /backup/metastore_$(date +%Y%m%d).sql
```

⚠️ 元数据丢失 = 所有表结构丢失，必须定期备份。

### 1.6.12 如何创建二级分区表？

```sql
CREATE TABLE log (
    id INT,
    msg STRING
)
PARTITIONED BY (dt STRING, hour STRING)  -- 二级分区
STORED AS ORC;
```

### 1.6.13 Union与Union all区别

- **UNION ALL**：合并结果集，**不去重**，速度快
- **UNION**：合并后**去重**（多一次排序去重操作），速度慢
- **生产建议**：优先使用 `UNION ALL`，去重在外层用 `GROUP BY` 或 `DISTINCT`

## 1.8 Maxwell

### 1.8.1 Maxwell与Canal、FlinkCDC的对比

🔥

| 对比项 | Maxwell | Canal | FlinkCDC |
|--------|---------|-------|----------|
| 开发语言 | Java | Java | Java |
| 输出格式 | JSON | 自定义 | Flink 内部格式 |
| 输出目的地 | Kafka/Kinesis/RabbitMQ | Kafka/RocketMQ/ES | Flink 下游 |
| 全量同步 | ✅ Bootstrap | ❌ | ✅ |
| 断点续传 | ✅（MySQL 元数据表） | ✅（ZK/内存） | ✅（Checkpoint） |
| HA | ❌（单节点） | ✅（主备） | ✅（Flink HA） |
| 使用场景 | 离线数仓增量采集 | 实时数据分发 | 实时数仓 |

### 1.8.2 Maxwell好处

1. **输出 JSON 格式**，开箱即用，对接 Kafka 方便
2. **支持 Bootstrap 全量同步**
3. **轻量级**，部署简单（一个 Java 进程）
4. **断点续传**，记录 Binlog Position 到 MySQL 表中

### 1.8.3 Maxwell底层原理

1. Maxwell 伪装成 MySQL 的 **Slave**
2. 向 MySQL Master 发送 dump 请求
3. MySQL 将 **Binlog**（ROW 模式）推送给 Maxwell
4. Maxwell 解析 Binlog Event，转换为 JSON 格式
5. 输出到 Kafka 等目的地

**前提**：MySQL 必须开启 Binlog 且格式为 `ROW`。

### 1.8.4 全量同步速度如何

- Bootstrap 全量同步：**约 10万~50万 条/分钟**（取决于 MySQL 性能和网络）
- 全量同步时会阻塞增量同步
- 大表全量同步可能需要几十分钟到几小时

### 1.8.5 Maxwell数据重复问题

Maxwell **可能产生重复数据**（如 Maxwell 重启、Binlog 重放），需要在下游做幂等处理：
- Kafka Consumer 端按主键去重
- 数据入库时用 `INSERT ... ON DUPLICATE KEY UPDATE`
- Flink 中用状态去重

## 1.9 DolphinScheduler调度器

### 1.9.1 每天集群运行多少指标?

根据项目规模，离线数仓每天运行 **100~300 个** 调度任务（Shell/SQL 任务），涉及 **几百个指标** 的计算。

### 1.9.2 任务挂了怎么办？

1. **告警通知**：DS 配置邮件/钉钉告警，第一时间发现
2. **查看日志**：DS Web UI 查看任务实例日志，定位错误原因
3. **自动重试**：配置任务失败重试次数（如 retry=2）
4. **手动修复**：修复问题后，在 DS 中对失败实例执行 **重跑**
5. **补数**：如果影响下游，需要从失败节点开始补数

### 1.9.3 DS挂了怎么办？

- DS **Master 支持 HA**：部署多个 Master 节点（通过 ZK 选举），一个挂了自动切换
- DS **Worker 支持多节点**：一个 Worker 挂了，任务会调度到其他 Worker
- 所有任务的调度记录和状态持久化在 **MySQL** 中，重启后自动恢复

1. **分区列表**（Partitions）：决定并行度
2. **计算函数**（Compute）：每个分区的计算逻辑
3. **依赖列表**（Dependencies）：窄依赖/宽依赖
4. **分区器**（Partitioner，可选）：KV 型 RDD 的分区方式（Hash/Range）
5. **优先位置**（Preferred Locations，可选）：数据本地性

### 1.10.4 RDD弹性体现在哪里

1. **存储弹性**：内存不够自动溢写磁盘
2. **容错弹性**：通过血缘关系（Lineage）自动重新计算丢失分区
3. **计算弹性**：Task 失败自动重试（默认4次）
4. **分区弹性**：可动态调整分区数（repartition/coalesce）

### 1.10.7 map和mapPartitions区别

🔥

| | map | mapPartitions |
|--|-----|---------------|
| 处理单位 | 一条数据 | 一个分区的所有数据 |
| 内存 | 低 | 高（一个分区的数据加载到内存） |

### 1.10.8 Repartition和Coalesce区别

| | repartition | coalesce |
|--|-------------|----------|
| Shuffle | **有** | 默认无（可指定 shuffle=true） |
| 增加分区 | ✅ | 需设 shuffle=true |
| 减少分区 | ✅ | ✅（**推荐**） |
| 场景 | 增加并行度 | 减少小文件/分区 |

### 1.10.9 reduceByKey与groupByKey的区别

🔥

| | reduceByKey | groupByKey |
|--|-------------|------------|
| Map 端预聚合 | **有**（Combiner） | **无** |
| Shuffle 数据量 | 小 | 大 |
| 性能 | **更好** | 较差 |
| 适用 | 聚合计算（求和、计数） | 需要完整分组数据 |

**结论**：能用 `reduceByKey` 就不要用 `groupByKey`。

### 1.10.10 Spark中的血缘

🔥 **Lineage（血缘关系）**：记录 RDD 的依赖关系链。

- **窄依赖**：父 RDD 的一个分区只被子 RDD 的一个分区使用（如 map、filter）→ 可以 Pipeline 执行
- **宽依赖**：父 RDD 的一个分区被子 RDD 的多个分区使用（如 groupByKey、reduceByKey）→ 有 **Shuffle**，划分 Stage 边界

**容错作用**：某个分区数据丢失，可以根据 Lineage 从父 RDD 重新计算，无需全量重算。

### 1.10.11 Spark任务的划分

🔥 **Application → Job → Stage → Task**

- **Application**：一个 SparkContext 对应一个 Application
- **Job**：一个 Action 算子触发一个 Job
- **Stage**：根据**宽依赖**（Shuffle）切分 Stage（DAGScheduler）
- **Task**：一个 Stage 中的一个分区对应一个 Task（TaskScheduler 调度）

### 1.10.14 Spark内核源码（重点）

🔥 **作业提交流程**：
1. SparkContext 初始化 → 创建 DAGScheduler + TaskScheduler
2. Action 算子触发 Job → DAGScheduler 划分 Stage（从后往前，宽依赖切分）
3. 最后的 Stage 为 **ResultStage**，之前的为 **ShuffleMapStage**
4. DAGScheduler 将 Stage 封装为 **TaskSet** 提交给 TaskScheduler
5. TaskScheduler 将 Task 分配到 Executor 执行
6. Executor 执行 Task，结果返回 Driver

### 1.10.15 Spark统一内存模型

🔥 **Spark 1.6+ 统一内存管理**：

Executor 内存 = **执行内存**（Shuffle/Join/Sort/Agg）+ **存储内存**（Cache/Broadcast）+ **其他内存**（用户代码）

- 执行内存和存储内存可**互相借用**
- 执行内存不足时可挤占存储内存（存储内存被挤占的部分会溢写到磁盘）
- 存储内存不足时可借用空闲的执行内存（但不能挤占正在使用的执行内存）
- 默认比例：执行 50% + 存储 50%（`spark.memory.fraction=0.6`，预留 40% 给用户代码和元数据）

### 1.10.16 Spark为什么比MR快？

🔥 **5个核心原因**：
1. **DAG 引擎**：优化执行计划，减少不必要的 Shuffle
2. **内存计算**：中间结果缓存在内存，MR 每个阶段都写磁盘
3. **JVM 复用**：Executor 进程常驻，MR 每个 Task 启动新 JVM
4. **Shuffle 优化**：Sort-based Shuffle + 数据文件+索引文件，减少文件数
5. **Pipeline 执行**：窄依赖算子在同一个 Task 内流水线执行，无需落盘

### 1.10.17 Spark Shuffle和Hadoop Shuffle区别？

| | Spark Shuffle | Hadoop Shuffle |
|--|---------------|----------------|
| 排序 | SortShuffle（可选不排序） | 必须排序 |
| 中间文件 | 数据文件 + 索引文件（2M 个文件） | 多个溢写文件合并 |
| Combiner | 可选 | 可选 |
| 内存使用 | 统一内存管理 | 环形缓冲区 |
| 落盘次数 | 更少 | 多次溢写 |

### 1.10.21 Spark操作数据库时，如何减少Spark运行中的数据库连接数？

🔥 使用 **`foreachPartition`** 代替 `foreach`：

```scala
rdd.foreachPartition { iter =>
  val conn = DriverManager.getConnection(url, user, pwd)
  iter.foreach { record =>
    // 使用 conn 写入数据库
  }
  conn.close()
}
```

**原理**：每个分区创建一个连接，而非每条数据一个连接。如 100 个分区 = 100 个连接，而非 100万条 = 100万个连接。

### 1.10.22 Spark数据倾斜

🔥 **解决方案**（按优先级）：

1. **提高并行度**：`spark.sql.shuffle.partitions=1000`（简单但效果有限）
2. **过滤异常 Key**：过滤空值或无意义的 Key
3. **两阶段聚合**：对 Key 加随机前缀预聚合，再去前缀二次聚合
4. **广播小表**：`broadcast(smallDF)` 做 Map Join，避免 Shuffle
5. **采样倾斜 Key**：对倾斜 Key 单独处理，其他正常处理，最后 UNION
6. **Salting（加盐）**：倾斜 Key 加随机后缀 + 另一侧膨胀N倍，分散数据后 Join
